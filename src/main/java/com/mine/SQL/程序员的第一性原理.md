# “程序员的第一性原理”指代：在写代码、做技术决策时，回到最根本的约束和事实去推导，而不是照搬惯例、框架或别人的做法。
对程序员来说，可以把它拆成几个层面来理解：
1. 计算机科学层面的第一性原理
    - 最底层的事实其实很朴素：
        - 计算就是状态变换：程序 = 数据结构 + 算法，本质是对状态的读取、判断、修改。
        - 资源是有限的：CPU 时间、内存、带宽、磁盘 IO、电量都是稀缺资源。
        - 抽象有成本：每一层抽象（框架、ORM、微服务）都在用性能/复杂度换取开发效率。
        - 复杂度守恒：问题本身的本质复杂度消不掉，只能转移或封装； accidental complexity（偶然复杂度）才是要尽力消除的。
    - 一切皆权衡：没有银弹，只有 trade-off。可读性 vs 性能、耦合 vs 复用、一致性 vs 可用性。
    - 这些是无论用什么语言、什么框架都不会变的东西。
2. 工程实践层面的第一性原理
    - 写代码时，回到最根本的问题：
    - 这段代码要解决什么问题？（而不是“别人都这么写”）
    - 输入是什么，输出是什么，边界在哪？
    - 如果从零设计，最简单的可行方案是什么？
    - 这个抽象是否真的降低了复杂度，还是只是把复杂度藏起来了？
    - 出错时会怎样？（失败路径往往比成功路径更重要）
3. 技术选型层面的第一性原理
    - 面对新技术、新框架时，不要因为“大厂在用”“社区很火”就选它，而是问：
        - 它解决的根本问题是什么？
        - 我当前的真实瓶颈是什么？
        - 引入它的成本（学习、运维、锁定）是否小于收益？
        - 如果不引入它，用最笨的办法能不能先跑通？
4. 一个经典例子
    - 马斯克常被引用的“电池成本”例子，在编程里对应的是：
        - 不要问“现在这个功能一般怎么做”，而是问“从物理/逻辑上，这件事最少需要几步、多少资源”。
        - 比如做缓存：不是一上来就上 Redis 集群，而是先问——数据量多大？访问模式是什么？一致性要求多高？也许一个本地 Map 就够了。
5. 但也别走极端
    - 第一性原理不是“什么都自己造轮子”。它的真正价值是：
        - 理解你依赖的东西为什么存在；
        - 在关键决策上不被惯性绑架；
        - 知道什么时候该用现成方案，什么时候该回到本质重新设计。
    - 一句话总结：
        - 程序员的第一性原理，就是不断追问“这个问题本质上是什么、最少需要什么”，而不是“别人通常怎么做”。

把“第一性原理”用到系统设计上，核心就是一句话：

不要从“别人怎么架构”出发，而是从“这个系统本质上要解决什么问题、受哪些物理约束”出发，一步步推导出架构。

下面按系统设计的实际决策顺序展开。

一、先回到最根本的约束
任何分布式系统，底层逃不出这几条铁律：

1. 网络不可靠

消息会丢、会重复、会乱序、会延迟。

所以：重试、幂等、超时、序列号、去重，不是“高级技巧”，是物理必然。

2. 磁盘和内存有限，且速度差几个数量级

内存 ns 级，SSD 微秒级，网络毫秒级，磁盘寻道毫秒级。

所以：缓存、分层存储、索引，本质都是在对抗这个速度差。

3. 一致性、可用性、分区容忍不可兼得（CAP）

分区一定会发生，所以真正要选的是：分区时保一致性还是保可用性。

再进一步：延迟和一致性也不可兼得（PACELC）。

4. 状态是复杂的根源

无状态服务可以随便扩，有状态服务才需要共识、复制、分片。

所以：能无状态就无状态，必须存状态时再面对复杂性。

5. 复杂度守恒

你消掉的复杂度不会消失，只会转移到别处（调用方、运维、数据修复）。

架构设计的一部分工作，是决定“把复杂度放在哪一层最划算”。

这些是无论用 AWS 还是自建机房、用 K8s 还是裸机，都不会变的东西。

二、从需求推导，而不是从技术栈推导
系统设计的第一性问题永远是：

要解决什么业务问题？

数据规模多大？（日活、QPS、数据量、增长曲线）

读写比例？（读多写少还是写多读少，差别巨大）

一致性要求？（强一致、最终一致、还是可以丢一点）

延迟要求？（P99 要多少毫秒）

可用性要求？（99.9% 还是 99.99%，成本差一个数量级）

失败时最坏后果是什么？（丢一条日志 vs 丢一笔钱）

例子：

如果是内部后台，日请求 1 万，那单体 + 一个数据库就是最优解，上微服务是负收益。

如果是支付核心，那幂等、对账、强一致就是第一性要求，性能可以往后放。

如果是 feed 流，读多写少、可容忍短暂不一致，那缓存 + 异步 fanout 就是自然选择。

关键：先算数量级，再谈架构。 很多架构争论，算一下 QPS 和数据量就结束了。

三、按“数据流”而不是“技术名词”来设计
不要一上来就说“我要上 Kafka / Redis / 微服务”。而是画出：

请求从哪来（客户端、网关、定时任务）

经过哪些处理（校验、鉴权、业务逻辑）

状态存在哪（数据库、缓存、对象存储）

结果怎么回去（同步返回、异步通知、轮询）

失败怎么办（重试、降级、补偿、人工介入）

然后针对每一段问：

这段的瓶颈是什么？（CPU、IO、网络、锁）

这段能不能无状态？

这段能不能异步？

这段出错会怎样？

架构是数据流和失败路径的自然结果，不是先选组件再拼起来。

四、几个从第一性原理推出的经典结论
1. 缓存为什么存在？
因为内存和磁盘/网络有速度差，且访问有局部性。没有这两点，缓存毫无意义。

2. 为什么要分片（Sharding）？
因为单机存储和写入有上限。分片本质是把一个大的有序/索引问题切成多个小的，代价是跨片查询和事务变复杂。

3. 为什么要副本（Replication）？
因为机器会坏。副本本质是用冗余换可用性和读扩展，代价是一致性。

4. 为什么要消息队列？
因为生产者和消费者速度不匹配，且需要解耦和削峰。它本质是一个有持久化的缓冲区。

5. 为什么要幂等？
因为网络会重试、消息会重复。幂等是把“至少一次”变成“效果上恰好一次”的唯一现实手段。

6. 为什么微服务不是默认答案？
因为分布式调用比进程内调用贵得多，且引入网络失败、数据一致性、运维复杂度。只有当团队规模、独立部署、技术异构等收益超过这些成本时才划算。

五、一个可操作的设计流程
遇到系统设计题或真实项目，可以这样推：

明确目标和约束：功能、规模、延迟、一致性、可用性、成本。

估算数量级：QPS、存储、带宽、机器数。

画最简数据流：客户端 → 服务 → 存储，先跑通。

找瓶颈和单点：哪里会先扛不住？哪里坏了会全挂？

逐个引入复杂度：缓存、队列、分片、副本、降级，每引入一个都问“不引入行不行”。

定义失败行为：超时、重试、幂等、补偿、监控、告警。

验证权衡：这个方案在规模翻 10 倍、机器挂一半时还能活吗？

六、一句话总结
系统设计的第一性原理，是从业务目标、数据规模和物理约束出发，推导出最简可行架构，并清楚地知道每一层复杂度换来了什么、代价是什么。

它反对的是：因为“大厂这么干”“面试要考”“显得高级”而堆技术。

如果你愿意，我可以接着用一个具体例子（比如设计一个短链系统、feed 流、或支付系统）完整走一遍这个第一性推导过程。


一、先问：支付系统本质上在解决什么？
剥掉所有界面和业务，支付的核心只有一件事：

在不可靠的网络和不可信的多方之间，安全地转移价值，并让所有参与方对“钱有没有动、动了多少”达成一致。

由此推出几个不可回避的本质约束：

钱不能凭空产生或消失 —— 必须守恒，任何环节都要能对账。

网络会重试、会超时、会重复 —— 所以“扣款”必须幂等。

你和银行/渠道是两个系统 —— 你无法原子性地同时改自己的账和对方的账，所以必须接受“中间态”，用状态机 + 补偿来收敛。

失败是常态，且失败点可能在任何一个环节 —— 尤其是“请求发出去了，但不知道对方成没成功”。

钱的事不能只靠最终一致就完事 —— 用户可以容忍延迟到账，但不能容忍账目对不上。

这五条决定了后面几乎所有设计。

二、明确目标和约束（先算数量级）
假设做一个中等规模、支持多支付渠道的支付平台：

功能：下单、支付、退款、查询、对账。

规模：日订单百万级，峰值 QPS 几千。

一致性：账务必须强一致（不能丢钱、不能重复扣）；通知用户可最终一致。

可用性：支付核心 99.99%，宁可短暂拒绝，不可错账。

延迟：支付接口 P99 < 1s（含渠道调用）。

合规：资金流水不可篡改，可审计。

关键判断：这不是一个“高并发读写”问题，而是一个正确性优先、可用性次之、性能再次的问题。方向定了，架构就不会跑偏。

三、核心模型：把“钱”抽象成账本
第一性推导：既然钱要守恒，那最自然的模型就是复式记账（Double-Entry）。

每一笔资金变动，都记为至少两条分录：一借一贷，金额相等。

账户余额 = 所有分录的汇总，而不是一个可随意改的字段。

任何时刻，全局借方总额 = 贷方总额。

为什么不用“用户表里一个 balance 字段直接加减”？

因为那样无法审计、无法对账、并发下容易错。

复式记账让“钱从哪来、到哪去”天然可追溯，这是支付系统的第一性数据结构。

典型账户：

用户账户

平台收入账户

渠道清算账户（对应微信/支付宝/银行）

手续费账户

退款/挂账账户

四、核心抽象：支付单 + 状态机
支付不是一个“动作”，而是一个有状态的过程。第一性推导：既然中间态不可避免，就要显式建模状态。

一个支付单的生命周期：

text
INIT（已创建）
  → PROCESSING（已提交渠道，结果未知）
  → SUCCESS（渠道确认成功）
  → FAILED（渠道确认失败）
  → CLOSED（超时关闭）
  → REFUNDING → REFUNDED（退款）
关键点：

PROCESSING 是最重要也最危险的状态：请求发出去了，但不知道渠道成没成功。

所以必须有主动查询 + 回调 + 定时补偿三管齐下，把 PROCESSING 收敛到终态。

状态流转必须单调、可审计，禁止回退（比如 SUCCESS 不能再变 FAILED，只能走退款）。

五、幂等：支付系统的生命线
第一性推导：网络会重试，用户会连点，渠道会重复回调。如果没有幂等，就会重复扣款。

做法：

每笔支付生成全局唯一的 支付单号（payment_id），由业务方传入或系统生成。

所有写操作以 payment_id 为幂等键：

创建支付单：INSERT ... ON CONFLICT DO NOTHING

扣款：基于状态机，只有 INIT/PROCESSING 才能流转，重复请求直接返回已有结果。

渠道回调：用渠道流水号 + 支付单号做唯一约束，重复回调直接忽略。

幂等不是加个去重表就完事，而是贯穿“请求—处理—回调—对账”全链路。

六、数据流与失败路径
正常支付流程
text
1. 业务方调用 创建支付单 → 落库 INIT
2. 调用渠道下单 → 落库 PROCESSING，记录渠道单号
3. 渠道异步回调 / 主动查询 → 确认结果
4. 成功：写复式记账分录，状态置 SUCCESS
5. 通知业务方（异步消息，可重试）
失败路径（重点）
失败点	后果	处理
创建支付单后崩溃	有 INIT 单无渠道单	定时任务扫描超时 INIT，关闭或重试
调渠道超时	不知道成功没	置 PROCESSING，靠查询/回调收敛
回调丢失	状态卡在 PROCESSING	定时主动查询渠道
记账时崩溃	状态和账不一致	记账与状态变更放在同一本地事务
通知业务方失败	业务方不知道结果	消息队列 + 重试 + 业务方主动查询兜底
核心原则：本地事务保证“状态 + 账务”原子；跨系统靠状态机 + 补偿 + 对账最终收敛。

七、对账：支付系统的最后防线
第一性推导：只要跨系统，就一定有对不上的时候。所以必须有一个独立的、周期性的核对机制。

渠道对账：每日拉取渠道流水，与本地支付单逐笔比对。

本地成功、渠道无 → 可能虚假成功，要冲正。

渠道成功、本地无 → 漏单，要补记。

金额不一致 → 人工介入。

内部对账：复式记账借贷是否平衡，账户余额与分录汇总是否一致。

对账不是补救措施，而是设计的一部分。没有对账的支付系统，等于没有安全网。

八、架构分层（由第一性推导，而非跟风）
text
接入层：API 网关（鉴权、限流、幂等入口）
业务层：支付服务、退款服务、订单服务
核心层：账务服务（复式记账）、状态机引擎
渠道层：渠道适配器（微信/支付宝/银行，统一接口）
异步层：消息队列（通知、重试、削峰）
保障层：对账服务、定时补偿、监控告警
存储层：关系型数据库（账务，强一致）+ 缓存（查询）
注意：

账务必须用支持事务的关系库，不能为了“高并发”上最终一致的 NoSQL。

渠道层要做适配器隔离，因为每家渠道协议不同，但核心账务不该感知。

微服务不是必须。如果团队小，支付+账务可以是一个单体，先把正确性做对。拆分的前提是独立部署、独立扩容、团队边界清晰。

九、几个常见但危险的误区
用余额字段直接加减 → 无法审计、并发错账。应用复式记账。

认为回调一定可靠 → 回调会丢、会重复、会乱序。必须主动查询兜底。

用分布式事务（2PC）跨渠道 → 渠道不支持，且性能差。应用状态机 + 补偿。

追求“实时强一致”跨系统 → 物理上做不到。接受中间态，用对账收敛。

先上微服务再想一致性 → 顺序反了。先保证单库事务内的正确性，再谈拆分。

把幂等当成加个 Redis 去重 → 幂等是状态机 + 唯一约束 + 全链路设计。

十、一句话总结
支付系统的第一性原理，是在承认网络不可靠、跨系统无法原子一致的前提下，用复式记账保证钱守恒，用状态机 + 幂等 + 补偿处理中间态，用对账兜底一切意外。

它的设计顺序永远是：正确性 > 可用性 > 性能 > 扩展性，而不是反过来。

下面用支付系统的场景，给出幂等的代码示例。重点不是“贴一段能跑的代码”，而是展示幂等在不同层次上分别怎么落地。

一、幂等的三个层次
在支付系统里，幂等不是单点技巧，而是分层的：

接口层：同一个请求重复到达，只处理一次。

状态机层：只有合法状态才能流转，重复流转被拒绝。

存储层：唯一约束兜底，数据库保证不重复写。

下面逐层给示例。

二、接口层：幂等键 + 去重表
表结构
sql
CREATE TABLE idempotency_record (
    idempotency_key VARCHAR(64) PRIMARY KEY,
    request_hash    VARCHAR(64) NOT NULL,
    status          TINYINT NOT NULL,        -- 0处理中 1成功 2失败
    response_body   TEXT,
    created_at      DATETIME NOT NULL,
    updated_at      DATETIME NOT NULL
);
处理逻辑（伪代码）
python
def handle_payment(idempotency_key: str, request: dict):
    request_hash = sha256(canonical_json(request))

    # 1. 尝试插入幂等记录，利用主键唯一约束抢占
    try:
        db.execute(
            "INSERT INTO idempotency_record "
            "(idempotency_key, request_hash, status, created_at, updated_at) "
            "VALUES (%s, %s, 0, NOW(), NOW())",
            (idempotency_key, request_hash),
        )
    except DuplicateKeyError:
        # 2. 已存在，读取已有记录
        record = db.query(
            "SELECT * FROM idempotency_record WHERE idempotency_key = %s",
            (idempotency_key,),
        )
        # 2.1 同一个 key 但参数不同 → 拒绝，防止 key 被复用
        if record.request_hash != request_hash:
            raise ConflictError("idempotency key reused with different request")

        # 2.2 还在处理中 → 让调用方稍后重试
        if record.status == 0:
            raise RetryLaterError("request in progress")

        # 2.3 已处理完 → 直接返回上次结果
        return json.loads(record.response_body)

    # 3. 首次请求，执行业务
    try:
        result = do_payment(request)
        db.execute(
            "UPDATE idempotency_record SET status = 1, response_body = %s, "
            "updated_at = NOW() WHERE idempotency_key = %s",
            (json.dumps(result), idempotency_key),
        )
        return result
    except Exception as e:
        db.execute(
            "UPDATE idempotency_record SET status = 2, response_body = %s, "
            "updated_at = NOW() WHERE idempotency_key = %s",
            (json.dumps({"error": str(e)}), idempotency_key),
        )
        raise
关键点：

用数据库主键唯一约束抢占，而不是“先查再插”——后者在并发下有竞态。

记录 request_hash，防止同一个 key 被不同请求复用。

状态为“处理中”时不能直接返回成功，否则会掩盖未完成的操作。

三、状态机层：只有合法状态才能流转
即使接口层漏了，状态机也要能挡住重复扣款。

支付单表

状态流转（带乐观锁）
python
ALLOWED_TRANSITIONS = {
    "INIT":        {"PROCESSING", "CLOSED"},
    "PROCESSING":  {"SUCCESS", "FAILED", "CLOSED"},
    "SUCCESS":     {"REFUNDING"},
    "FAILED":      set(),
    "CLOSED":      set(),
}

def transition(payment_id: str, from_status: str, to_status: str) -> bool:
    if to_status not in ALLOWED_TRANSITIONS.get(from_status, set()):
        return False

    # 乐观锁：只有当前状态和版本都匹配才更新
    rows = db.execute(
        "UPDATE payment_order SET status = %s, version = version + 1, "
        "updated_at = NOW() "
        "WHERE payment_id = %s AND status = %s AND version = %s",
        (to_status, payment_id, from_status, current_version),
    )
    return rows == 1
关键点：

状态只能沿允许的方向走，SUCCESS 不能再变 FAILED。

用 WHERE status = 旧状态 做条件更新，天然防并发重复流转。

重复回调到达时，发现已经是 SUCCESS，直接返回成功，不重复记账。

四、存储层：唯一约束兜底
账务分录是钱的最终记录，必须防重复。

分录表

python
def write_entry(payment_id, account_id, direction, amount, biz_type):
    try:
        db.execute(
            "INSERT INTO ledger_entry "
            "(payment_id, account_id, direction, amount, biz_type, created_at) "
            "VALUES (%s, %s, %s, %s, %s, NOW())",
            (payment_id, account_id, direction, amount, biz_type),
        )
    except DuplicateKeyError:
        # 已经记过账，幂等忽略
        return
关键点：

唯一键 (payment_id, biz_type, account_id, direction) 保证同一笔业务同一账户同一方向只记一次。

即使上层逻辑重复调用，数据库也会挡住。

五、把三层串起来：一次支付回调
python
def on_channel_callback(callback: dict):
    payment_id = callback["payment_id"]
    channel_no = callback["channel_no"]

    # 1. 渠道流水号去重（防渠道重复回调）
    if not try_insert_channel_callback(channel_no):
        return "OK"   # 已处理过，直接应答

    # 2. 加载支付单
    order = load_payment(payment_id)
    if order is None:
        return "OK"

    # 3. 已经是终态 → 幂等返回
    if order.status in ("SUCCESS", "FAILED", "CLOSED"):
        return "OK"

    # 4. 状态机流转 + 记账，放在同一个本地事务
    with db.transaction():
        ok = transition(payment_id, "PROCESSING", "SUCCESS")
        if not ok:
            return "OK"   # 状态已被其他请求改掉，幂等忽略
        write_entry(payment_id, order.user_account, 1, order.amount, "PAY")
        write_entry(payment_id, order.channel_account, 2, order.amount, "PAY")

    # 5. 异步通知业务方（可重试，业务方也要幂等）
    mq.publish("payment_success", {"payment_id": payment_id})
    return "OK"
关键点：

渠道流水号去重 → 状态机 → 唯一约束，三层防护。

状态变更和记账在同一个本地事务里，保证“状态和账”原子。

对外通知走 MQ，允许重复，由业务方自己幂等。

六、几个容易踩的坑
先查再插有竞态

并发下两个请求可能都查到“不存在”，然后都插入。

正确做法：直接 INSERT，靠唯一约束捕获冲突。

幂等键用业务参数拼

比如 userId + amount + timestamp，几乎必然重复。

应该由调用方生成全局唯一 key，或系统生成 payment_id。

把“处理中”当成成功返回

调用方以为成功了，实际可能失败。

应返回明确状态，或让调用方轮询查询。

只做接口幂等，不做状态机幂等

内部重试、MQ 重投、定时补偿都可能绕过接口层。

状态机和唯一约束是最后防线。

幂等记录和业务不在同一事务

业务成功但幂等记录没更新，重试会重复执行。

二者要么同库同事务，要么用状态机兜底。

七、一句话总结
幂等的本质是：用唯一键抢占 + 状态机约束 + 存储层唯一约束，把“可能重复的请求”收敛成“只生效一次”。

接口层挡大部分，状态机挡内部重试，数据库唯一约束挡一切漏网之鱼。
